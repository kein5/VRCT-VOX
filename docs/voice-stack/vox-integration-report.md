# VRCT-VOXへの統合記録

2026年10月30日。プロジェクトの改名、画面全体の刷新、開発環境と配布パイプラインの整備を行いました。既存のTTS・RVC・モデル取得機能も統合対象に含めています。

## 名前と互換性

GitHubリポジトリは[kein5/VRCT-VOX](https://github.com/kein5/VRCT-VOX)へ改名しました。既定ブランチはdevelopです。README、アプリ名、実行ファイル、配布物、CIとサポート先を新名称にそろえました。

既存設定を引き継げるよう、アプリID、Linuxの設定・データ保存先、`VRCT_*`環境変数、仮想マイクの所有識別子は維持しています。原著作権、ライセンス、過去の実測結果に記録された配布物名も残しました。詳細は[互換性の説明](project-rename.md)にあります。

## 画面

濃紺の背景と青い操作色を、メイン画面、設定、Quick Chatの共通スタイルへ反映しました。サイドバー、言語選択、チャット入力、設定の見出し、TTS・RVC・モデル取得フォームを整えています。

狭いウィンドウではサイドバーを自動的に縮めます。キーボードのフォーカス表示、設定を閉じた後のフォーカス復帰、ボタンの読み上げ名、動きを減らす設定にも対応しました。モデル取得の同意と適用、音声の開始と停止は別操作のままです。

[PRODUCT.md](../../PRODUCT.md)と[DESIGN.md](../../DESIGN.md)に画面の目的と設計ルールを記録しました。構成要素の記録は`.impeccable/design.json`です。

## 開発と配布

`.editorconfig`とCocogittoを追加しました。`tools/dev.py`から環境診断、明示的な依存導入、対象を選んだ検証を実行できます。通常の検証ではアプリやマイクを起動しません。Unix向けの開発用sidecar準備は、所有記録とハッシュが一致するファイルだけを更新します。[開発手順](../development.md)にコマンドとWindowsの制限をまとめました。

LinuxとWindowsの配布候補には、コミット、版、ファイル集合、サイズ、SHA-256を記録します。インストーラー用のチェックサムも候補検証とdraftへのコピーに含めます。draft作成は手動で、同じdevelopコミットの成功した候補だけを受け付けます。同名タグがすでにある場合や、照会に失敗した場合は停止します。公開は自動化していません。[配布手順](release-candidates.md)を参照してください。

## 統合と未確認の範囲

既存の113コミットと今回の実装コミット`52c2ddb8`を、`28ae5917`でdevelopへマージしました。マージ前後のコードは同一です。他の作業ブランチはdevelopの祖先に当たり、未統合のコミットはありません。元の作業環境とブランチは保持しています。統合後の独立checkoutでも、CIと同じLinux補助バイナリを準備し、音声契約1,199件と共通quick検証の成功を確認しました。

Cocogitto導入前の`79044ab5`には`wip:`形式のコミットが1件あるため、履歴を書き換えず記録を残します。新しいコミットは`895d9cfe`以降を基点に検証しています。今後のPRではdevelopとの共通祖先以降を対象にします。

Windowsでのインストール、実GitHub draftの作成・公開は未実施です。今回のAppImage試験は画面と起動の確認であり、以前のTTS遅延測定や実RVC試験を新名称の候補で再認証した結果ではありません。音声の実測条件は[低遅延記録](tts-low-latency-report.md)と[RVC検証記録](rvc-index-search-report.md)を参照してください。

初回のGitHub CIでは、Ubuntu標準のPipeWireヘッダーに必要なAPIがなくコンパイルに失敗しました。CIは固定版PipeWire 1.6.10とWirePlumber 0.5.18を隔離ビルドする構成へ修正しています。既存の時刻・不連続検査を維持し、未対応版のクライアントライブラリやdaemonではcaptureを開始しない検査を追加しました。詳細と同じ環境を用意する手順は[Linuxビルド手順](linux-build-pipeline.md)にあります。

WindowsのCIで見つかったHTTP受信待ちの取消も修正しました。短い内部タイムアウトで取消を確認し、HTTPのバッファと元の受信期限は維持しています。接続状態の取得には共有workerを1本だけ使い、取得が遅れた場合は結果を不明として扱います。取得処理自体は中断できず、停止した取得処理が最大1本残る可能性がありますが、音声終了処理ではその完了を待ちません。

最終レビューに修正必須の指摘は残っていません。軽微な改善候補として、停止直後にTCP確認を1回行う経路があります。状態取得の待機上限は50ms、通常の接続確認は100msです。これらは処理の設定値であり、OSのスケジューリングを含む終了時間や実機で聞こえるまでの遅延を保証する値ではありません。
