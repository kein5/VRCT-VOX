# 利用者向けドキュメントの構成の見直し 設計

日付: 2026-11-14
状態: 承認済み（2026-11-14。英語の画面は「サイトに全部そろえる」）

## 目的と理由

利用者向けサイト（`site/ja`、`site/en`）を、読みやすくわかりやすい構成にする。あわせて、アプリと
サイトで機能の名前をそろえ、自分のモデルや購入したモデルを使う方法を案内する。

依頼（2026-11-14、ユーザーの言葉）:

- 「ユーザーが読みやすい&わかりやすいドキュメントになるように見直してくれない？」
- 「トップページや設定の「TTS」も「テキスト読み上げ（TTS）」または「チャット読み上げ（TTS）」にする。」「「RVC」も「音声変換（RVC）」または「ボイスチェンジャー（RVC）」にする。」「OCRとASRも同様の記述にするのがユーザーに分かりやすいと思う。」
- 「バンドルされたモデルや規定のモデル以外にも自前のモデルまたは購入したモデルを導入する方法もUI上やgithub pagesのユーザー向けドキュメントで案内してあげるといいんじゃないかな。」

調査の結果は `~/research/user-docs-structure/`（`digest.html`、`report.html`）。設計に効いた原文は次のとおり。

- 利用者の 79% は新しいページを拾い読みし、1語ずつ読むのは 16%（NN/g）。簡潔な版は 58%、拾い読みしやすい版は 47% 使いやすかった。
- 見出しは最初の2語ほどしか見られない（NN/g）。
- マニュアルを使わない理由に「役に立つ検索語が見つからない」が挙がる（Novick & Ward 2006）。
- 手順は道具の操作ではなく利用者のやりたいことから書く（Diátaxis）。目次は機能ではなく利用者の観点で組む（@IT 谷口 2010）。
- 道具の文書でも、仕組みの全体像を示すページがあるとよい（Wayne 2023）。リファレンスは対象の構造に合わせて並べる（Diátaxis）。
- 画面の画像は、画面全体を写して指示の横に置くと学ぶ時間が 25% 減った（van der Meij 2000）。
- 利用者は手順の途中で行き詰まってから文書を開き、その部分だけを知りたがる（UXmatters 2007）。

## 目標

1. 目的から探せる入口がある。「翻訳した文を VRChat に送る」のような、やりたいことの言葉でページへたどり着ける。
2. 声と文字がどこを通ってどこへ出るかを、1ページで見渡せる。
3. どの機能のページも同じ型で、拾い読みで「何ができるか」「何が要るか」「どう始めるか」「止め方」がわかる。
4. アプリの画面とサイトで、機能の名前が同じ。略語（TTS、RVC、ASR、OCR）には日常の言葉の名前を添える。
5. 自分のモデルや購入したモデルを使う方法が、サイトとアプリの両方から見つかる。

## 目標にしないこと

- Diátaxis の4種類どおりにページを全部分けること（ユーザーが案 C を選ばなかった。ページ数が倍以上になり、日英の保守が重い）。
- アプリの機能や設定の挙動を変えること。変えるのは表示の名前、説明の文、ドキュメントへのリンクだけ。
- 内部識別子（設定のキー、IPC、`tts`、`rvc` などの id）を変えること（AGENTS.md の互換性の境界）。
- 新しいモデルをカタログに載せること、モデルを取得すること。

## してはいけないこと（失敗とみなす）

- アプリの文言の変更で、ボタンを押したときの動作が変わる。マイクの有効化、モデルの取得、送信が勝手に起きる。
- 日本語と英語のどちらかだけを直す。
- 狭いウィンドウや長い日本語で、ボタンやメニューの名前が切れて読めなくなる。
- 自分のモデルの案内で、利用条件の確認を省いてよいと読める書き方をする。許諾の無い声や作品を使うよう勧めて読める書き方をする。

## 案の比較（ユーザーが B を選んだ）

| 案 | 中身 | 得るもの | 失うもの |
|---|---|---|---|
| A | ページの並びはそのまま。各ページの型をそろえる | 変更が小さい | 目的から探す入口と全体像が無いまま |
| **B（採用）** | A に加えて「やりたいこと」の入口と、全体像のページを足し、サイドバーを組み直す | 検索語が分からない人と、全体像が欲しい人に答えられる。機能のページは設定画面の並びと合ったまま残る | ページが3つ増える |
| C | Diátaxis どおりに機能ごとにハウツー・リファレンス・解説を分ける | 型が厳密 | ページ数が倍以上。日英の保守が重い。道具の文書には分けすぎ |

## 決めたこと

### 1. サイトの構成（サイドバー）

```
はじめに
  VRCT-VOXとは
  インストール
  最初の設定
  声と文字の流れ（新規・全体像）
やりたいこと（新規）
  やりたいことから探す（新規・目的の一覧）
  自分のモデルを使う（新規）
機能の詳細
  翻訳
  音声認識（ASR）とリアルタイム字幕
  テキスト読み上げ（TTS）
  ボイスチェンジャー（RVC・Seed-VC）
  チャット読み取り（OCR）
  VRとオーバーレイ
  入力と出力
  入力の小窓とホットキー
  OBSとWebSocket
設定と運用
  モデルの取得
  Linuxの音声経路
  困ったとき
  プライバシー
  ライセンスと謝辞
```

- ページの URL（`/ja/features/tts` など）は変えない。アプリが `guide/troubleshooting` と `guide/first-setup` を直接開くため（`src-ui/logics/ui_configs.js:123-124`）。新しいページだけ新しい URL にする。
- 英語も同じ並び。

### 2. 「やりたいことから探す」のページ（`guide/tasks`）

やりたいことを見出しにして、1つごとに「要るもの」「手順の要点（3行ほど）」「詳しいページへのリンク」を置く。見出しは目的の動詞で始める。並べる項目（案）:

- 翻訳した文を VRChat のチャットボックスに送る
- 自分の声を文字にして送る
- 相手の声を字幕で見る（自分の画面、VR の中）
- 相手のチャットボックスの文を読んで訳す
- 訳した文を声で届ける
- 自分の声を別の声に変えて届ける
- 話した言葉の訳を、変換した自分の声で届ける
- 配信（OBS）に字幕を出す
- 自分のモデルや購入したモデルを使う
- いま声と文字がどこへ出ているかを確かめる

トップページ（`index.md`）の「はじめる」の横に、このページへのボタンを足す。

サイトの検索も日本語の言葉で引けるようにする（私の判断）。いまの VitePress のローカル検索は空白と記号でしか語を区切らないので、「テキスト読み上げ（TTS）」の中の「読み上げ」のような語で引けない見込みが高い。`Intl.Segmenter` で日本語を語に区切る設定を `config.mts` の検索に足し、ビルドした検索の索引で「読み上げ」「仮想マイク」が引けることを確かめる。

### 3. 「声と文字の流れ」のページ（`guide/how-it-works`）

入力（マイク、相手の声、チャット入力、相手のチャットボックス）から、処理（音声認識、翻訳、読み上げ、ボイスチェンジャー）を通って、出口（チャットボックス、仮想マイク、字幕、ログ、OBS）へ出るまでを、1枚の図と短い説明で示す。仮想マイクがなぜ要るかもここで説明する。

図は描いた図（SVG）にする（私の判断）。「入力と出力」のパネルは自分の声とチャットの2つしか示さず、相手の声と相手のチャットボックス、ログ、OBS が無いため。パネルのスクリーンショットは「いまの設定でどこへ出るかを確かめる」節に置き、パネルのページへリンクする。図の中の名前は、下の「機能の名前」とそろえる。

### 4. 機能のページの型

各機能のページを次の順にそろえる。見出しが合わない節は無理に作らない。

1. 冒頭の2文: 何ができるか、どこで設定するか。
2. 「必要なもの」: モデル、GPU、別に入れるもの。
3. 「はじめて使う」: 番号付きの手順。画像はその手順のすぐ下に置く（ページの先頭にまとめない）。
4. 用途ごとの節: 見出しは「〜する」「〜を変える」のように、何をするかで始める。
5. 「止める」: 止め方と、止まる範囲。
6. 「うまくいかないとき」: そのページの機能の症状だけ。詳しくは「困ったとき」へリンク。
7. 「確かめた範囲」: ページの最後に、`::: details` で畳んで置く（いまは本文の途中にある所がある）。

文の書き方:

- 1段落に1つのこと。結論を先に書く。
- 設定の一覧は表にする。
- 日本語は yomiyasu を通し、読点を減らし、段落と改行と箇条書きを増やす（ユーザーの指示、メモリ `japanese-wording-fewer-commas`）。

### 5. 機能の名前（アプリとサイトで共通）

アプリの画面で利用者が機能の名前として目にする所を、次の名前にする。

| 機能 | 日本語 | 英語 | いまの表示（日本語／英語） |
|---|---|---|---|
| 読み上げ | テキスト読み上げ（TTS） | Text to speech (TTS) | TTS ／ TTS |
| 声の変換 | ボイスチェンジャー（RVC） | Voice changer (RVC) | RVC ／ RVC |
| 音声認識 | 音声認識（ASR） | Speech recognition (ASR) | 音声認識 ／ Transcription |
| チャット読み取り | チャット読み取り（OCR） | Chat reading (OCR) | チャット読み取り ／ Chat Transcribe |

英語の画面は本家 VRCT の名前（Transcription、Chat Transcribe、Voice2Chatbox、Speaker2Log）が残っていて、英語のサイトの名前と食い違う。英語の画面をどこまで変えるかは、ユーザーに確かめる（下の「ユーザーに確かめること」）。

候補からこう選んだ理由（ユーザーが変えてよい）:

- 読み上げは、チャットの入力だけでなく、マイクの発言の訳も読む。「チャット読み上げ」だと、マイクの訳を読むことが伝わらない。
- 声の変換は、アプリの設定の説明にすでに「ボイスチェンジャー」とあり、Seed-VC のモードも「ボイスチェンジャー（試験的）」という名前。VRChat の利用者には「音声変換」より通じやすい。

変える場所:

- メイン画面のスイッチ（`MainFunctionSwitch.jsx` の `tts` と `rvc` は文字列を直書きしているので、`locales` のキーに移す）。
- 設定の左のメニュー（`config_page.side_menu_labels`）と、各ページの見出し（`tts_settings.label`、`rvc_settings.label`、`VoiceSettings.jsx`、`DirectVoiceSettings.jsx`）。
- ホットキーの名前（`useHotkeys.js`、`Hotkeys.jsx` の `name: "TTS"`、`name: "RVC"`）。
- 文の中でスイッチの名前を指している所（例「トップ画面でTTSをオンにしてください」）。
- 通知の見出し（`MainFunctionSwitch.jsx` の `notify(..., "TTS")`、`notify(..., "RVC")`）。
- 「入力と出力」の図の箱の名前（`io_flow.output.speech`「読み上げ」、`io_flow.conversion`「声の変換」など）。
- サイトのページ題、サイドバー、トップページ。
- メイン画面のスイッチ「チャット読み取り」も「チャット読み取り（OCR）」にする（私の判断）。DESIGN.md の「メイン画面のスイッチと設定のページは同じ名前」に合わせるため。
- メイン画面のスイッチ「マイク入力」「聞き取り」は、名前をそのまま残す。ASR の名前は設定のメニューとページ題に付ける。理由: スイッチは入力の向き（自分と相手）を区別する名前で、2つとも「音声認識（ASR）」にすると見分けられない。いまも設定のページ「音声認識」とは名前が違う。

長い名前の置き方（私の判断）:

- メイン画面の左の列は幅 240px で、名前に使える幅は 14px の文字で約 124px。「テキスト読み上げ（TTS）」は約 165px で1行に入らない。
- 「（」の前で2行に分ける（「テキスト読み上げ」「（TTS）」）。略語の行は小さめの文字にして、行の高さの差を抑える。どこで折れるか分からない折り返しにはしない。
- 列の幅は変えない（DESIGN.md の配置を守る）。短い名前に戻してツールチップに逃がすことはしない（ユーザーの依頼に反する）。
- VR の設定ウィンドウの左のメニュー（`side_menu_labels` を使う）と、「入力と出力」の箱（VR のウィンドウとデスクトップの表示を含む）も同じ考えで、狭い幅で撮って確かめる。

文の中の扱い:

- 利用者に行き先を指す文（「TTSの設定で出力デバイスを選んでください」「トップ画面でTTSをオンに」）は、新しい名前を「」で書く。例「「テキスト読み上げ（TTS）」の設定で出力デバイスを選んでください」。
- 行き先を指さない文（「TTSのみ：0.5 GiBを残す」など）は、短い名前「TTS」「RVC」のままでよい。新しい名前に略語が入っているので、画面で一度見た人には通じる。

変えない場所: 内部の id、設定のキー、IPC と OSC の名前、ログの文。

### 6. 自分のモデルを使う案内

アプリが自分のファイルやサーバーを受け付ける所と、受け付けない所（2026-11-14 にコードを読んで確かめた）:

| 機能 | 自分のものを使えるか | 指定する所 | アプリが確かめること |
|---|---|---|---|
| テキスト読み上げ（TTS） | GGUF のモデルと、声の GGUF（任意）。または手元で動く外部サーバー | 設定 →「テキスト読み上げ（TTS）」→「モデルとサーバー」の「モデルGGUFのパス」「声GGUFのパス（任意）」。声の GGUF は声名に `custom` と入れて使う | 拡張子 `.gguf` と、先頭の `GGUF` の4バイトだけ（`src-python/models/speech_server/settings.py:43-55`）。起動後に読み上げ用のモデルかを確かめる（`runtime.py:244-250`） |
| 音声認識（ASR） | GGUF の認識モデル、VAD、話者分離（任意）。または手元の外部サーバー | 設定 →「音声認識（ASR）」→「モデルとサーバー」→「ASR + VAD」 | 同じ。起動後に認識と区切りのモデルかを確かめる |
| Whisper | 手元のファイルは使えない。OpenAI 互換の Whisper サーバーなら使える | 設定 →「音声認識（ASR）」の「カスタムWhisperサーバー」 | 保存時に接続とモデルの一覧を確かめる。HTTP はこの PC かローカルネットワークだけ |
| ボイスチェンジャー（RVC） | `.pth` のモデルと `.index`（任意） | 設定 →「ボイスチェンジャー（RVC）」 | 拡張子と、ファイルがあること。読み込むときに RVC v1 か v2、標本化周波数 32k・40k・48k かを確かめる（`integrations/rvc/loader.py:142-146`） |
| Seed-VC | 参照の WAV（1〜30 秒） | 設定 →「高度な設定」→「入力音声の転送」 | PCM の WAV として読めることと、長さ（`integrations/seed_vc/offline.py:28-36`） |
| 翻訳 | ローカルの翻訳モデル（CTranslate2）は一覧のものだけ。LM Studio、Ollama、OpenAI 互換サーバーに入れたモデルなら使える | 設定 →「翻訳」→「ローカルLLM・互換サーバー」 | 接続の確認 |
| チャット読み取り（OCR） | 使えない（ハッシュが一致した一覧のモデルだけ） | — | — |

サイトに足すもの:

- 新しいページ「自分のモデルを使う」（`guide/custom-models`）。上の表を先頭に置き、機能ごとに「使えるファイル」「指定する手順」「うまくいかないとき（出るメッセージ）」を書く。見出しには日英で共通のアンカー（`{#tts}`、`{#asr}`、`{#whisper-server}`、`{#rvc}`、`{#seed-vc}`、`{#translation}`）を付け、アプリから節を直接開けるようにする。
- 購入したモデルと配布されているモデルの節: 使う前に提供元の利用規約を読むこと（VRChat で使ってよいか、配信や録画で使ってよいか、クレジットの表示、改変、再配布）。アプリは自分で指定したファイルの利用条件を確かめないこと。実在する人の声を使うときはその人の許可が要ること。モデルのファイルをほかの人に渡さないこと（規約で許されている場合を除く）。
- 「モデルの取得」のページの「手元のファイルを指定します」から、このページへリンクする。
- 声の GGUF と声名 `custom`、外部サーバーの URL、カスタム Whisper サーバーは、いまどのページにも書かれていないので、このページで初めて説明する。対応するモデルの系統は speech.cpp の資料で確かめてから書く（推測で書かない）。

アプリに足すもの:

- 各モデルの欄の説明の近くに「自分のモデルを使う方法」のリンクを置く。押すとブラウザで、表示言語のサイトの該当する節を開く。置く所: 「モデルとサーバー」（`SpeechServers.jsx`、TTS と ASR）、「ボイスチェンジャー（RVC）」（`DirectVoiceSettings.jsx` の RVC）、「入力音声の転送」（Seed-VC）、翻訳の「ローカルLLM・互換サーバー」、「カスタムWhisperサーバー」。
- リンクは `src-ui/logics/ui_configs.js` の `generateLocalizedDocumentUrl` に定数を足して作り、設定の画面で外部リンクを開く既存の `openUrl` の流れ（`ModelDownloads.jsx` など）で開く。開けないときは既存の `model_downloads.link_error` を出す。
- リンクを押してもブラウザが開くだけで、設定、モデル、音声には何も起きない。

一緒に直すこと（文書から参照するのに要るため）:

- RVC と Seed-VC のエラーの一部（`vc_options_invalid`、`vc_runtime_missing`、`vc_model_missing`、`vc_engine_format_invalid`、`vc_index_failed`、`reference_duration`、`reference_local_file`）は、日本語と英語の文言が無く、コードがそのまま出る（`locales/ja.yml:53` のコメント）。文言を足す。どう表示されるかは実装の前に確かめる。
- 起動画面の「困ったとき」のリンクが、表示言語にかかわらず英語のページを開く（`SplashComponent.jsx:54`）。表示言語のページを開くようにする（私の判断。小さい修正で、文書への入口に関わるため）。

今回は直さないこと:

- 声名を間違えたときに、読み上げのエラーが HTTP の番号のまま出る（`speechcpp_tts.py:272-273`）。文書の「うまくいかないとき」で「声名が `custom` か確かめる」と案内するにとどめ、別の作業として報告する。

## ユーザーに確かめたこと

1. 英語の画面の名前をどこまで変えるか → 「サイトに全部そろえる」。Text to speech (TTS)、Voice changer (RVC)、Speech recognition (ASR)、Chat reading (OCR) にし、メイン画面の Voice2Chatbox と Speaker2Log も日本語の「マイク入力」「聞き取り」に合わせて Mic input と Listening にする。
2. この設計（4つの名前を含む）で進めてよいか → 「この設計で進める」。

## 私が決めたこと（読むときに確かめてほしい所）

- 「声と文字の流れ」の図は描いた図にし、パネルのスクリーンショットは別の節に置く。
- サイトの検索に日本語の語の区切りを足す。
- メイン画面の「チャット読み取り」も「チャット読み取り（OCR）」にする。
- 長い名前は「（」の前で2行に分け、左の列の幅は変えない。
- 起動画面の「困ったとき」のリンクを表示言語のページにする。

## 検証

- `python tools/dev.py check`、`check --scope ui`（文言とコンポーネントを変えるため）。
- サイトのビルド（`site/` で `npm run build`。VitePress はリンク切れで失敗する）。

- コミットは `check --scope commits --base origin/develop`。
